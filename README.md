# Diplom_2

## Коллега, для установки зависимостей выполни команду: 

    pip3 install -r requirements.txt


## Для запуска теста с созданием отчётов Allure запусти поочерёдно:
    
    *Для тестирования:
    pytest --alluredir=allure_results
    
    *Для визуализации отчётов:
    allure serve allure_results
    
    *Для визуализации отчётов в конкретной папке:
    allure generate C:\***адрес***\allure_results -o C:\***адрес***\Allure_Report
    
    *Чтобы открыть отчёт запустите в терминале:
    allure open Allure_Report


## Найденные дефекты

### BUG-001. Документация противоречит сама себе в части авторизации при создании заказа

**Тип:** дефект документации (расхождение разделов между собой и с фактическим поведением)
**Приоритет:** Medium — блокирует определение ожидаемого результата для тест-кейса

**Где:** «Документация API» — раздел «Создание заказа» (с. 1) против раздела
«Авторизация и регистрация» (с. 5).

**Суть расхождения:**

Раздел «Авторизация и регистрация» (с. 5) прямо запрещает анонимные заказы:
> Только авторизованные пользователи могут делать заказы. Структура эндпоинтов
> не меняется, но нужно предоставлять токен при запросе к серверу в поле `Authorization`.

Раздел «Создание заказа» (с. 1) описывает `POST /api/orders` без единого упоминания
авторизации: тело запроса состоит только из массива `ingredients`, заголовок
`Authorization` не фигурирует ни в описании, ни в примере. При этом приведён пример
успешного ответа:

```json
{
  "name": "Краторный метеоритный бургер",
  "order": { "number": 6257 },
  "success": true
}
```

Ключевая деталь: в этом примере объект `order` содержит единственное поле `number`.
Это структура ответа именно на **анонимный** запрос. Авторизованный запрос возвращает
расширенный объект с полями `_id`, `owner`, `price`, `status`, `ingredients`,
`createdAt`, `updatedAt`. То есть документация приводит ответ неавторизованного
запроса в качестве эталонного примера успешного создания заказа.

**Шаги воспроизведения:**

1. Получить хеши ингредиентов: `GET /api/ingredients`
2. Выполнить `POST /api/orders` с телом `{"ingredients": [<3 валидных хеша>]}`
   **без** заголовка `Authorization`

**Фактический результат:** `200 OK`, заказ создан, присвоен номер.
Поведение соответствует разделу «Создание заказа» и противоречит разделу
«Авторизация и регистрация».

**Ожидаемый результат:** единая трактовка в обоих разделах документации. Возможны
два варианта, и документ не позволяет выбрать между ними:
- если верна с. 5 — сервер должен отвечать `401 Unauthorized`
  с `{"success": false, "message": "You should be authorised"}`, и тогда это дефект реализации;
- если верна с. 1 — требование авторизации на с. 5 следует убрать или переформулировать
  как относящееся только к UI (переадресация на `/login`), и тогда это дефект документации.

**Влияние на тестирование:** для тест-кейса «создание заказа без авторизации»
ожидаемый результат неопределим — оба возможных ассерта (`200` и `401`) обоснованы
разными разделами одного и того же документа.
